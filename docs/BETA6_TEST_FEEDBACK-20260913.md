# 0.5.0-beta.6 实测反馈（2026-09-13）

状态：集中收集，尚未修复。记录当前正式数据上的可复现实测，不把自动化通过等同于用户验收通过。

## F01 反推返回可用 JSON，却被判为整轮失败

- 范围：已有标签反推与接入；来源列“上衣样式”。
- 操作：24 件首轮样本，模型 `CS/z-ai/glm-5.3-flash`，点击反推后又点击一次继续/重试。
- 现象：界面显示“反推任务尚未生成标准草案”“本轮任务失败”。
- 真实记录：两次文字请求分别约 81.5 秒和 87.4 秒；每次输出均达到 8192 tokens，`finish_reason=length`，视觉请求均为 0。
- 关键缺陷：第二次响应实际是可解析的完整 JSON，已含总定义、8 个已有值规则、4 个冲突和未知策略；通用请求层在解析和结构校验前，仅凭 `finish_reason=length` 就丢弃响应。
- 额外缺陷：本轮证据字段保存为 Excel 原始列“图片”，没有映射为内部“商品主图”输入，因此 310 件有图却估算为 0 张图片、0 次视觉请求。界面同时展示“图片”和“商品主图”，含义容易混淆。
- 误导文案：失败卡统一声称“已成功保存的视觉组合在重试时复用”，但本轮不存在视觉组合。
- 期望：先解析并校验响应；合法结果应进入审核并标记截断风险。真正不完整时只补缺失区块；模型完全失败时仍生成明确标注来源的程序基线草案。原始图片列应自动映射真实资产或从选择器中消歧。
- 验收点：相同已保存响应无需再次付费即可恢复；重复重试不得原样重发；审核页准确显示文字/视觉请求数和恢复来源。

## F02 新建对话长时间零反馈，且没有自动超时

- 范围：新建网页对话；对话名“新对话”。
- 用户输入：`判断上衣样式，我人工打了一些标签可以结合图片做参考`。
- 开始时间：2026-09-13 18:17:01（Asia/Shanghai）。
- 中间检查：18:20:47 仍为 `running`；助手正文 0 字、可见进度事件 0 条、错误码为空。
- 最终结果：约 18:27:55 结束，状态 `failed`、错误码 `tool_permission_denied`，整轮耗时约 10 分 54 秒。
- 运行证据：独立 Reasonix 进程存活；18:17:24 至 18:19:41 至少产生 8 条模型调用统计，最新一次上下文约 22355 tokens。说明最初确实在工作，不是按钮没有触发。
- 直接卡点：Reasonix 调用 `ask_business_question` 时，`product_workbench` MCP 等待满 5 分钟后超时；同轮还尝试调用协调器未开放的 `run_skill`，被权限层阻止。技术诊断记录 `MCP call timed out ... ask_business_question timeout=5m0s`。
- 放大原因：会话入口等待 `session/prompt` 时使用无限总超时；内部模型和工具活动没有及时成为网页可见阶段。一次问题桥接超时因此表现为长时间“没反应”，最后主错误又只显示禁止工具，没有突出造成长等待的 5 分钟超时。
- 归类问题：简单意图被扩展为过长的多工具链；业务提问桥接阻塞；禁止工具与超时错误的主因选择不准确；进度不可见；缺少首字节、静默和总时限。
- 期望：首个可见事件应在数秒内出现；持续显示模型调用数、最近活动时间和当前阶段。业务问题应及时形成网页问题卡；达到静默阈值时提示“仍在工作/可能卡住”，达到总时限后中断并保留会话，可从同一对话恢复。
- 验收点：同类请求不能在零文本状态等待数分钟；超时后保留已完成工具结果和原会话，可从未完成步骤继续；停止按钮在限定时间内结束等待并解除数据集 busy 状态；不得把内部多轮模型调用伪装成一次无期限回复。

## 合并修复时的共同原则

- 保存已经产生的有效结果和成功阶段，不因后续阶段失败而清空。
- 重试只处理缺失部分，并在执行前显示预计请求数。
- 界面展示真实阶段、最近活动时间、文本/视觉调用数及明确错误，不使用与实际阶段不符的通用文案。
- 任何降级结果必须标明“程序基线”“模型已核验”或“视觉未执行”，不能把降级输出伪装成完整模型结论。
