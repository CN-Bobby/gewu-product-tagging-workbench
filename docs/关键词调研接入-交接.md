## 5. 本轮修掉的两个真实缺陷（都只在打包环境才现形）

### 5.1 MCP 传输解包长度（`000ea4a`）

- 现象：每次调用都在传输层崩，`ValueError: too many values to unpack (expected 2, got 3)`，两轮均在 8-9 秒失败
- 根因：工作台锁定 `mcp 1.29.1`，其 `streamable_http_client` 会 yield **三个**值（多一个 session-id 取值器）；桌面版 pin 的 `mcp 2.1.1` 只有**两个**。移植代码按两个解包
- 修：解包改为 `(read, write, *_)`，对两个 SDK 版本都成立
- 证据：新增 `tests/test_keyword_research_transport.py`（回环起最小 MCP 服务，用生产 `MCPClient` 真打一次 initialize → tools/call → 解析 → 调用日志）；变异检查——把解包改回二元组，该测试报出同一个 `ValueError`（1 failed），还原后通过
- **为什么离线抓不到**：`FakeMCP` 覆写的正是 `_call_once`，也就是真实传输那一层

### 5.2 引擎子进程的兄弟 import（`ac6cefb`）

- 现象：打包后 `validate_labels.py` 起子进程即 `ModuleNotFoundError: No module named 'classify_keywords'`（第 1 轮其实已把 150 个关键词标注完，倒在这一步）
- 根因：随包 runtime 是**孤立型解释器**（`flags.safe_path=True`、`isolated=1`，等价 `-I`）——它既不把「脚本所在目录」放进 `sys.path`，也忽略 `PYTHON*` 环境变量（实测 `PYTHONPATH` 无效）；开发 venv 两样都正常，于是**离线全绿、打包必崩**。原实现里那句 `sys.path.insert(0, SCRIPTS_DIR)` 正是为此存在，改成子进程时被丢掉
- 修：子进程改为「引导 + `runpy`」：先注入引擎脚本目录，再以 `__main__` 跑目标脚本；`command_for(script, extra_args, scripts_dir)` 暴露这个形状
- 证据：`tests/test_keyword_research_run.py::test_engine_command_bootstraps_the_scripts_dir` 用 `-I` 模拟打包环境做正反两面实证；变异检查——去掉引导改回直接执行，测试报 `ModuleNotFoundError`（1 failed），还原后通过；另用**真实随包 runtime** 验证：原导出错误消失、脚本正常执行

## 6. 未决项

### 6.1 矩阵开的真实产物尚未拿到（P0）

三次尝试都倒在 LLM 标注阶段，失败点在报告之前、与矩阵逻辑无关。两种失败：模型返回「数组里混入非对象」（`llm_label.py` 的严格校验如实拒绝）、以及并发下到模型端连接被拒。
→ 建议：先处理 6.2，再补跑一次矩阵开；否则「矩阵开关在真实产物上验过」这句话不成立（离线那层已验）。

### 6.2 标注阶段的鲁棒性（P0）

- 模型偶发返回非对象行时，当前策略是重试若干次后**整轮失败**（第 5 次实测 15 个批次里 6 个命中，其中批次 6 连试 3 次未过）。拆半重试目前只用于截断场景，形状错误未用
- 3 路并发批标注 + 本机代理环境下出现 `WinError 10061`（目标积极拒绝）：`llm_client` 的重试是否覆盖连接层错误、退避是否足够，需要核对
- 两条都属引擎内部契约/鲁棒性改动，按纪律需配红测试

### 6.3 与打标联动（P1，本轮明确不做）

结论不进打标数据集、不参与标签判断。后续若做，走既有只读引用或提案通道，**不改**「外部资料不成本商品事实」这条契约。

### 6.4 第二条模型调用路径（P1）

关键词调研保留引擎自身的调用语义（Responses→Chat 回退、截断拆半重试），与工作台的直连批处理并存。合并属低层契约变更，需独立一轮。
