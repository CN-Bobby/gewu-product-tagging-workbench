### 文字底稿

- 原文件 352 行的「标题」都有内容，但 `dataset.mapping.title=null`。`backend/importer.py` 的标题别名缺少「标题」；正文仍保留在 raw 中，未丢失，但自动底稿与协调员默认读取没有包含它。
- 原字段「图片链接」「详情页链接」也未映射；内嵌图片已经导入，不能把链接映射缺失解释为内嵌图片不可用。父ASIN已映射；无子ASIN时当前 anchor 回退到 SKU，界面身份含义也应改善。
- 73 行的错误是 `'list' object has no attribute 'get'`。`text_facts.execute` 对返回对象及 results 元素直接调用 `.get`，缺少对象类型检查；其拆批分支处理 ValueError/KeyError/TypeError，却不处理 AttributeError。因此结构异常会直接使剩余批次失败。原始异常返回未保存，无法确定每次是顶层数组还是嵌套数组，也不能断言 73 行都独立发出了坏请求。
- Excel 第2行有保留的拒绝候选：原文键为 `parameters` / `详细参数`，模型证据写成 `参数`。这是来源键不匹配，不是该行没有尺码。例中 Size: X-Large 有可定位证据。
- `text_facts.for_batch` 以整条底稿成功作为门槛。只读 SKU 的尺码任务，也会被无关颜色、护理或其他属性的底稿失败阻断。继续标签任务不会自动修复其上游底稿。
- 尺码规则已经明确取区间上界和年龄分档，仍走模型路径，缺少受控文字解析＋数值映射能力。

### 错误诊断信息丢失

`batch.group` 把 `attributes.validate_result` 的具体 ValueError 丢弃，最后统一报「部分商品结果缺失或不符合标签候选值」。缺商品、值不在候选、逐属性证据不一致等不同问题因此无法区分；没有保存拒绝候选。对这批视觉标签，现有记录不足以逐条给出更细错误归因。修复必须先补响应结构、校验位置、实际候选和重试链记录，不能把所有错误都归给模型。

## 2. 局部修正、范围和新旧标签混跑

底层已有按 product_ids 修正和执行，但 MCP 没有按原字段、标签值、单元格状态或任务失败集查询范围的工具。read_tasks 只返回前10个错误；read_worksheet 虽可分页，返回大量行内容，缺少轻量 ID/范围查询。

下午实际对话因此只准备了12行失败试点；用户提出「件数标签=2」也无法直接转成服务端筛选范围。协调员声称全量必须由用户逐行选中并不完全正确：`draft.propose` 实际允许省略 product_ids，默认全表，但 MCP 说明和固定提示没有把这个能力说清楚。局部条件范围确实缺失。

前端 `main.jsx` 的执行弹窗明确使用当前可见列，查看范围与执行范围耦合；切换数据集也重新显示所有列。15:33 的实际抽样提案同时带了「尺码段」和「下装样式」，旧列6个失败项确实被夹带。默认不覆盖已完成值，所以不是所有旧成功格都会重算；旧失败、待处理项仍会进入新任务。

Excel 第83行保留了「SKU Size:14 → 青少年teen」成功结果及任务21aa…来源，同时 status=failed，附加通用错误。重复任务能把其他任务已成功的格改成失败；`batch.fail` 只检查人工 edit 和本任务 completed，不验证最新执行归属。需要单元格任务所有权／代次保护，包括失败写入路径。

## 3. 对话与提案流程

18条助手回复中8条 status=failed，这8条的事件均含 `ask` → permission_denied → 提前停止 error。工作台只开放5个MCP能力，未提供可用提问桥接；CLI尝试其提问能力时被拒绝。应把澄清接入网页或约束为普通对话，不能靠开放Shell等无关权限解决。

当前固定提示明确要求先确认新增列，再读取新列ID，另提执行。用户说「确认了」时仍会生成待确认建列提案，后续还需界面再生成执行提案。来回操作是协议设计造成的，应改成一个可审阅的复合提案：定义、执行范围、覆盖策略、图片策略一起展示，由用户一次明确确认。

16:37和16:46的回复提醒旧两列「未执行」，但旧任务在16:07已创建并有大量成功结果；这是任务状态解读错误。18:01又称拆出的7列正在执行，并建议从界面删除7列恢复；实际只有迁移后的结果，没有这7列的独立执行任务，也没有对应删除列界面/API。这些是协调员能力与状态描述失真。

## 4. 图案和款式识别

目前仅取每商品第一个本地图片。视觉阶段输出自由文本 observation，之后文字模型依据观察填表。没有逐部件区域、可见性、多个候选的结构化判别，也没有可用给协调员的抽样看图工具。方案讨论主要读取文字样本，不等于全局视觉识别。

已保存规则存在明显风险：

- 印花花型冲突规则写「无法确认归属时归入更具体的候选」，应当保留不确定或较宽类别，不能在证据更弱时更具体。
- `floral→碎花/小花`、`straps→细肩带`、`tankini/halter→齐腰常规` 把不等价概念当同义词，容易引导错误。
- 肩带粗细与背部走向混在同一类别，本身可能同时命中。缺少明确单选/多选约束；下午确实触发并确认整类拆列，不能通过一句「互斥单选」自动保证后端行为。
- 印花列写了依赖构成列，但 definition 没有 depends_on。Excel第72、119、144、350行分别出现纯色/纯色拼接与条纹/格纹并存，违反其已确认口径。
- 图像抽查仅2张，不足以给352件款式准确率；没有用户指定的错标金标准，不能把推测当逐件结论。需要保留实际错例，按部件/可见性改规则后做前后盲测。

## 5. 文字联合、图文混合和全局识别的实际能力

底稿设计是同一商品的 SKU＋参数＋标题一起输入，不是每个原字段独立分析；这次标题因映射缺失漏入。标签任务按标签列分别执行，每列带自己的 fields。`source=text` 读取所选文字；`source=both` 将文字/底稿与视觉观察交给后续文本模型；`source=image` 不附商品文字字段，即使定义中写了 SKU 也不会读取。

所以代码存在图文合用路径，但不是同一多模态请求直接联合看图和读文字。本次6个视觉标签都配置 image，未实现讨论中某些「SKU辅助」承诺。视觉模型拿到的是图片与定义，不含该商品的实际 SKU/标题内容。

当前无完整的全局画像机制：有逐行文字底稿、分页抽读，没有全表属性分布、覆盖率、冲突分布、代表性图片抽样汇总及指导后续规则的统一报告。

知识库/主动检索也未接入协调员：仅本地Skill规则和工作表工具。应设计有来源、时间、品类适用范围的参考资料检索，把外部知识用于提示机会和解释术语，不用于伪造本商品事实。本次没有进行外网产品研究。

## 6. 性能与任务收尾

|任务|保存的总请求数|视觉请求数|墙钟时间|
|---|---:|---:|---:|
|下装全量|404|325|303.16秒|
|纯色＋花型|880|690|621.48秒|

这是记录中的该次执行指标；继续任务会重置指标，不能当跨重试累计。视觉请求不是请求「批次数」：代码逐列循环，并逐商品调用视觉。三列不等于一次图片请求，协调员「一起识图不增加成本」的说法错误。

SSE已有增量传送，但每个进度事件保存整个job（含定义、expected、completed等）。本数据集3001条job事件payload字符量约493.62 MiB（SQLite length字符统计口径；JSON主要转义保存），正式DB约570 MiB。这是已量化的重复内容，不是500MB商品数据；实际网络字节和浏览器CPU本轮未剖析，不能报它们的精确耗时。

6个partial任务是已结束带失败，不是6个还在后台运行。界面只能继续、查看详情，部分失败任务无归档/作废/替代入口，取消接口也不改变partial状态。MCP反复读取最近任务，因此旧失败持续进入对话。需要分离执行历史与当前待处理问题：修复/重跑后标记已解决或被替代，保留证据但不持续提醒。
